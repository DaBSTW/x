# ROADMAP.md — Ruta de trabajo

> Plan de ejecución derivado de [`SPECS.md`](./SPECS.md).
> Cada tarea es una unidad de trabajo con salida verificable.
>
> **Duración estimada:** 18 semanas hasta producto completo (fases 0–3).
> **Equipo asumido:** 3–4 personas (2 backend, 1–2 frontend, infra compartida).

---

## Cómo leer este documento

- `[ ]` tarea pendiente · `[x]` completada
- **🔴 Bloqueante** — nada avanza hasta que esté hecho

### 1.2 Grafo social 🔴

- [x] `POST/DELETE /users/:id/follow` con actualización de contadores
- [x] `GET /users/:username/followers` y `/following` paginados
- [x] Caché en Redis de la lista de seguidos (`SET`, TTL 1 h) para el timeline

- [x] `GET /users/suggestions` (SPECS.md §5.4): cuentas más seguidas que el caller aún no sigue, excluyéndose a sí mismo — un solo `LEFT JOIN`, sin bullet propio en la versión original de este roadmap; se añadió al construir el estado vacío del timeline en 1.8
- [x] `blocks` y `mutes` (tablas + endpoints — la aplicación en filtros sigue yendo en fase 2, deliberadamente sin tocar aquí: nada en timeline/notificaciones/búsqueda lee estas tablas todavía). Mismo patrón que `follows` en cada capa: `CHECK` de no-auto-bloqueo/silencio en el propio esquema (no solo en el servicio), `POST`/`DELETE /users/:id/block` y `/mute` simétricos a `/follow`. Bloquear es exclusivo con seguir en ambas direcciones — el `INSERT` en `blocks` y el `DELETE` de cualquier `follows` mutuo (con sus contadores) ocurren en la misma transacción, para que un bloqueo nunca conviva con una fila de `follows` obsoleta. Silenciar no toca `follows` en absoluto: es unidireccional y silencioso por diseño, la persona silenciada nunca se entera.

### 1.3 Timeline cronológico 🔴

> La pieza de mayor riesgo técnico de esta fase. Empezar por aquí.

- [x] Publicar evento `post.created` en **BullMQ** (Kafka se introduce en fase 3)
- [x] **Worker de fan-out** (`apps/workers`):
  - [x] Lote de 1000 seguidores por pipeline de Redis
  - [x] `ZADD timeline:{uid}` + `ZREMRANGEBYRANK` (retener 800) + `EXPIRE` 7 días
  - [x] Idempotencia — `SET NX` sobre `fanout:processed:{postId}` (el `postId` es el `event_id`: cada post publica como máximo un evento `post.created`)
- [x] Umbral de **cuenta grande** (≥10 000 seguidores): marcar y excluir del fan-out
- [x] `GET /timeline/home`: merge de Redis + posts recientes de cuentas grandes seguidas
- [x] **Reconstrucción perezosa** del timeline frío desde PostgreSQL (siembra el ZSET al reconstruir, así la siguiente lectura vuelve a ser un hit de Redis)
- [x] **Hidratación en lote**: un solo `WHERE id = ANY($1)` (`PostsService.getManyByIds`). ⚪ Caché de objeto en Redis para el post ya hidratado: diferido — interactúa con la invalidación por contador de 1.4 (likes/reposts), que aún no existe; añadirla antes tendría TTL/invalidación incorrectos garantizados.
- 🟡 Test de carga (k6): 1000 timelines concurrentes, verificar p95 < 200 ms (`apps/api/load-tests/`) — script + fixtures listos y ejecutados de verdad contra Postgres/Redis/API reales, no simulados. En este sandbox de 4 vCPUs compartidas: p95 = 134 ms a 50 VUs (pasa), p95 = 2.57 s a 1000 VUs (no pasa) con 0% de errores en ambos casos y throughput casi idéntico — el patrón típico de saturación de CPU de un único proceso Fastify sin clúster compitiendo por 4 núcleos con Postgres/Redis/k6, no un endpoint lento. La cifra de 1000 VUs / p95 < 200 ms asume la topología horizontal de SPECS.md §14 (múltiples instancias tras balanceador); no se puede certificar en un solo contenedor. Detalle en `apps/api/load-tests/README.md`.
- [x] Test: fan-out de cuenta con 100 k seguidores completa en < 5 s (`apps/workers/load-tests/fanout-scale.ts`) — ejecutado de verdad contra Postgres/Redis reales (Testcontainers): **2.70 s** con 100 000 seguidores reales, por debajo del presupuesto de 5 s

### 1.4 Interacciones 🟡

- [x] `POST/DELETE /posts/:id/like` — contador en Redis primero (`post:{id}:counters` HASH, `HINCRBY`; 1000/24h por usuario)
- [x] `POST/DELETE /posts/:id/repost` — crea post de tipo `repost` (`text IS NULL`) vía `PostsService.repost`, entra en el fan-out igual que cualquier post
- [x] `POST/DELETE /posts/:id/bookmark`
- [x] **Worker de agregación de contadores** (`apps/workers/src/counters/`): `SPOP` sobre `dirty:post_counters` cada 5 s, agrupado por `post_id`, `UPDATE post_counters` (Redis es autoritativo para el valor, no un delta)
- [x] Job nocturno de **reconciliación** (`apps/workers/scripts/reconcile-counters.ts`): recalcula desde `likes`/`bookmarks`/`posts` para publicaciones con actividad en 24h. Verificado con datos reales (Testcontainers) corrigiendo un drift simulado. Falta el cron externo que lo dispare cada noche — tarea de ops, no de código (ver docs/adr/0003).
- [x] Test de concurrencia: 100 likes simultáneos → contador exacto al final — ejecutado de verdad (Testcontainers): 100 `like()` concurrentes sobre el mismo post, `post:{id}:counters` en Redis termina en exactamente 100

- [x] Campo `viewer` (`liked`/`reposted`/`bookmarked`) del ejemplo de respuesta de SPECS.md §5.4, en `GET /timeline/home`: lookup en lote (`IN`-query) por like/bookmark/repost del caller sobre la página ya hidratada — la ruta ya exige autenticación, así que no hace falta el auth opcional que motivó el diferimiento original. `GET /posts/:id` ya expone `viewer` también, cerrado en este checkpoint: el auth opcional que motivaba el diferimiento ya existía de hecho (`optionalAuth` llegó con 2.6 para el filtrado por bloqueos/cuentas protegidas de esa misma ruta) — nadie había vuelto a conectar el campo. `posts.service.ts` gana un `ViewerStateLookup` (mismas tres formas que `timeline.service.ts` ya usaba, reexportado desde ahí para no duplicar el tipo — timeline depende de posts como su `PostHydrator`, nunca al revés) y un helper `withViewerState` de un solo post, aplicado en `getById`; `getThread` lo hereda gratis para su propio campo `post` (construido vía `getById`), pero `ancestors`/`replies` (`getManyByIds`) siguen sin él — alcance idéntico al bullet original, no ampliado en silencio. `app.ts` reordena la creación de `interactionsRepository` para que quede disponible antes que `postsService` (antes se creaba después, solo para `interactionsService`/`timelineService`). Cubierto con fakes en `posts.service.test.ts` y, contra Postgres real, en `posts.integration.test.ts` (like/bookmark/repost reales vía las rutas HTTP, comprobando que un viewer distinto sin interacción lee `false` en los tres campos). ⚪ Hueco real encontrado después, sin cerrar todavía: la propia ruta `GET /posts/:id/thread` ya calcula `viewer` correctamente en el servidor (hereda `getById`, arriba), pero `app/[username]/status/[id]/page.tsx` la consume vía `server-api-client.ts`, deliberadamente anónimo (mismo motivo que la nota de 1.6 sobre el perfil) — así que el post enfocado, sus ancestros y sus respuestas nunca traen `viewer` de verdad, y el botón de "Me gusta"/repost/guardar en esa página nunca refleja el estado real, aunque la petición al backend sí funcione. `use-post-mutations.ts` gana un `router.refresh()` tras cada mutación (mismo patrón que `ProfileEditDialog`/`ThreadReplyComposer`), que sí mantiene los contadores públicos al día ahí, pero no puede arreglar `viewer` por el mismo motivo que un `router.refresh()` no ayudaba con `viewer.following` en 1.6: la re-petición al servidor sigue siendo anónima. Arreglarlo de verdad pediría el mismo patrón que `use-profile-viewer-state.ts` — un fetch cliente autenticado — pero aplicado a una lista de posts (ancestros + enfocado + respuestas), no a uno solo; encontrado con `notifications-grouping.spec.ts` (que sí pasa, cambiando su propia aserción para no depender del botón), no oculto.

### 1.5 Multimedia — imágenes 🟡

- [x] `POST /media/upload-url` → URL prefirmada de S3/MinIO + `media_id`. Simplificado frente al diagrama de flujo de SPECS.md §9.1 (PUT presignado directo, sin `fields` de un POST presignado multiparte) — el bullet del roadmap solo pedía "URL prefirmada + media_id", y un PUT único es un cliente mucho más simple sin perder ninguna propiedad de seguridad.
- [x] `POST /media/:id/finalize` → valida (síncrono, feedback inmediato) y encola procesamiento (asíncrono, cola `media-processing` de BullMQ, `apps/workers` como consumidor)
- [x] **Validación por magic bytes**, nunca por `Content-Type` del cliente — sniff de la firma real (JPEG/PNG/WebP/AVIF/HEIC) antes de aceptar el archivo, cubierto con tests contra buffers reales (no inventados a mano)
- [x] Protección contra bomba de descompresión (límite de píxeles totales) — `sharp`/libvips `limitInputPixels` en el momento de decodificar variantes (worker), más una comprobación explícita de ancho/alto en `finalize` (API) antes de encolar nada
- [x] **Strip completo de EXIF** (crítico: elimina geolocalización), aplicando orientación al píxel — `.rotate()` graba la orientación en los píxeles; no llamar a `.withMetadata()` después es lo que realmente elimina el resto del EXIF (comportamiento por defecto de sharp). Verificado con una imagen real etiquetada con orientación EXIF 6 en el test unitario del worker.
- [x] Worker con `sharp`: variantes WebP + AVIF en 4 anchos (340/600/1200/orig) — "orig" es el ancho propio de la imagen, nunca upscaled por encima del original
- [x] Generación de **blurhash** para placeholder
- [x] Adjuntar hasta 4 imágenes a un post; `alt_text` editable (`PATCH /media/:id`). El adjuntado es atómico dentro de la misma transacción que crea el post: la cláusula `WHERE` de la actualización (`owner_id` = autor, `status = ready`, `post_id IS NULL`) es la propia validación — si algún id no encaja, la transacción entera revierte.
- [x] Límite: 5 MB, 8192×8192 máx.
- [x] Reintentos (`attempts: 3`, backoff exponencial) en la cola de procesamiento — no es un bullet explícito de esta sección, pero a diferencia de fan-out/notificaciones (sin red de seguridad si fallan, pero autocurables: fan-out por reconstrucción perezosa, SPECS.md §6.1), un transcode fallido no tiene fallback, así que sí justifica reintentos reales; el estado terminal `failed` se escribe solo cuando se agotan.
- ⚪ Lo que queda fuera de este checkpoint, explícitamente: GIF/vídeo (SPECS.md §9.2, fases posteriores), escaneo ClamAV/CSAM, evento WebSocket `media.ready` (no hay `ws-gateway` todavía — fase 2), cabeceras CDN de entrega. Ninguno es un bullet de esta sección.

### 1.6 Perfiles 🟡

- [x] `GET /users/:username` — perfil público, con contadores (followers/following/posts) desde `user_counters`
- [x] `PATCH /users/me` — display name, bio, ubicación, web, y ahora `avatarMediaId`/`bannerMediaId`: se resuelven contra la infraestructura de media de 1.5 (owned + `status = ready` + `kind = 'image'`, mismo criterio que adjuntar media a un post) y el servidor escribe la URL resuelta en `avatarUrl`/`bannerUrl` — el cliente nunca guarda una URL a mano. Cerrado en este checkpoint el hueco de UI que quedaba anotado aquí: `<ProfileEditDialog>` (nuevo, botón "Editar perfil" en `<ProfileHeader>` sólo en el propio perfil, mismo patrón de remontar por `key` que `<AltTextDialog>` de 1.8) cubre displayName/bio/ubicación/web y sube avatar/portada reutilizando el mismo flujo de subida que el composer — extraído a `lib/upload-image.ts` (`uploadImage`, `validateImageFile`) para que `use-media-upload.ts` y este diálogo compartan exactamente los mismos cuatro pasos (`upload-url` → PUT → `finalize` → poll) en vez de duplicarlos. `useUpdateProfile` (antes fijado a sólo `isProtected`) se generalizó a `UpdateUserInput` completo. `websiteUrl` exige URL válida a nivel de schema — no hay forma de vaciarlo una vez puesto a través de este endpoint, así que el diálogo simplemente omite el campo si se deja en blanco en vez de mandar una cadena vacía inválida; hueco real y separado, no algo que este diálogo pueda resolver por su cuenta. Al probarlo de punta a punta con Playwright real aparecieron dos huecos genuinos, no hipotéticos: (1) `app/[username]/page.tsx` es un Server Component real (SPECS.md §7.2) — `useUpdateProfile`'s `onSuccess` sólo tocaba la query cliente `['users','me']`, así que el perfil servido no se refrescaba hasta que `router.refresh()` se añadió (mismo patrón que ya usa el `onPosted` del composer); (2) el bucket de MinIO nunca tuvo política de lectura pública — cada URL que `buildPublicUrl` construye devolvía 403 a un fetch anónimo real, invisible hasta ahora porque nada anterior comprobaba que una imagen *cargara* de verdad (un `<img>` roto sigue siendo "visible" en el DOM; `<Avatar>` de Radix sí hace su propia carga real antes de pintar nada). `packages/utils/src/s3.ts`'s nuevo `ensurePublicBucket` (idempotente: crea el bucket si falta, aplica la política siempre) corre ahora en el arranque real de `apps/api` (`server.ts`, no `app.ts` — `scripts/generate-openapi.ts` también construye la app y no necesita tocar S3 de verdad) y en `global-setup.ts` — el mismo hueco habría afectado en silencio a *cualquier* imagen servida por la app, no sólo avatares
- [x] Página de perfil con **SSR** (`app/[username]/page.tsx`, React Server Component real — `fetch` server-side contra `GET /users/:username`, sin pasar por el cliente autenticado del navegador) para SEO. Nuevo `lib/server-api-client.ts` deliberadamente sin `getAccessToken`: reusar el singleton del navegador aquí habría compartido estado mutable de un store de Zustand entre requests concurrentes de distintos usuarios. Esta ruta dinámica expuso un hueco real: un username como `home` quedaría permanentemente tapado por la ruta estática `/home` de Next.js — `usernameSchema` ahora rechaza una lista de nombres reservados antes de que eso pueda pasar, no después.
- [x] Metadatos Open Graph y Twitter Card por perfil (`generateMetadata`) y por post (`app/[username]/status/[id]/page.tsx`, nuevo — SSR contra `GET /posts/:id`, el `username` de la URL es cosmético, el id es el canónico). `<PostCard>`'s timestamp ahora enlaza ahí, igual que el permalink de la referencia.
- [x] Pestañas: Posts / Respuestas / Media / Me gusta — `GET /users/:username/posts?filter=` (nuevo parámetro), cursor-paginado igual que antes. Posts/Respuestas separan por `kind`; Media es un `EXISTS` contra `media` (no un `JOIN`, que duplicaría filas con hasta 4 adjuntos); Me gusta va por la tabla `likes` en vez de por autoría, y ordena por el id del post — no por el momento del like — para reusar el mismo cursor Snowflake que el resto de listas en vez de un keyset nuevo sobre `(likes.created_at, post_id)`. Cerrado en este checkpoint el hueco de `viewer.following` que quedaba anotado aquí: `GET /users/:username` gana `optionalAuth` (mismo patrón que `GET /posts/:id`, 1.4) y un nuevo campo `viewer: {following, requested}` (`profileViewerStateSchema`, packages/contracts) — dos lookups, no uno, porque una cuenta protegida (2.6) puede tener una solicitud *pendiente* sin llegar a seguir todavía, y `<FollowButton>` necesita distinguir ese tercer estado ("Solicitud enviada") de los otros dos. `profiles.service.ts`'s `withViewerFollowState` omite `viewer` entero cuando no hay `viewerId`, no hay dependencia conectada, o el viewer es el propio dueño del perfil (nadie se sigue a sí mismo) — mismo contrato "ausente, no `false`" que ya documentaba post.ts. ### 3.2 Timeline algorítmico 🔴

- [ ] **Etapa 1 — Candidate generation** (~1500 candidatos, 50 ms)
  - [ ] In-network 50 % — posts de seguidos en 48 h
  - [ ] Out-of-network por grafo 25 % — engagement de tus seguidos (2.º grado)
  - [ ] Out-of-network por embeddings 15 % — pgvector o Qdrant
  - [ ] Tendencias y temas 10 %
- [ ] **Etapa 2 — Ranking** (30 ms): LightGBM servido vía ONNX Runtime
  - [ ] Pipeline de features: post, autor, relación, espectador
  - [ ] Entrenamiento offline con datos de ClickHouse; reentrenamiento semanal
- [ ] **Etapa 3 — Heurísticas** (10 ms)
  - [ ] Máx. 2 posts consecutivos del mismo autor
  - [ ] Dedupe de contenido por SimHash
  - [ ] Dedupe de vistas con Bloom filter por usuario en Redis (10 k entradas, FP < 1 %)
  - [ ] Inyección de contexto social ≤ 15 %
- [ ] **Degradación obligatoria**: > 100 ms o error → timeline cronológico, nunca un 5xx
- [ ] A/B testing con métricas de engagement antes de activarlo por defecto

> ⚠️ **No adelantar esta sección.** Sin datos de entrenamiento suficientes, el
> ranking produce un feed peor que el cronológico. Requiere ≥ 4 semanas de datos
> de interacción reales en ClickHouse.

### 3.3 Moderación 🔴

- [ ] **Capa preventiva** (< 100 ms, síncrona): listas de bloqueo, Safe Browsing, límites de menciones
- [ ] **Capa automática** (asíncrona): clasificadores de toxicidad, spam y NSFW
  - [ ] `> 0.95` → acción automática · `0.70–0.95` → cola humana · `< 0.70` → sólo log
- [ ] **Capa reactiva**: `POST /reports` + priorización por reputación, alcance y gravedad
- [ ] Acciones graduadas: etiqueta → reducción de alcance → ocultación → eliminación → modo lectura → suspensión → baneo
- [ ] Registro inmutable en `moderation_actions` con motivo y política aplicada
- [ ] **Flujo de apelación** con notificación al usuario incluyendo el fragmento infractor
- [ ] Panel `apps/admin`: cola de revisión, historial de acciones, búsqueda de cuentas
- [ ] Antispam: score de confianza por cuenta, límites para cuentas nuevas (10 posts/día, sin enlaces 24 h)
- [ ] Detección de coordinación: clustering por SimHash, timing y huella de red

### 3.4 Rendimiento 🟡

- [ ] Réplicas de lectura + enrutamiento; **read-your-writes** durante 5 s tras escribir
- [ ] PgBouncer en modo `transaction`
- [ ] Anti-estampida: locks de reconstrucción (`SET NX PX 5000`) y jitter ±10 % en TTLs

- [ ] Presupuesto de bundle en CI: falla si la ruta inicial supera 180 KB gzip
- [ ] Core Web Vitals reales (RUM): LCP < 2.5 s, INP < 200 ms, CLS < 0.1
- [ ] Campaña de carga con k6: 50 k QPS de timeline, 5 k posts/s

## Reglas de trabajo permanentes

Aplican en **todas** las fases, no son tareas de una fase concreta:

- Ninguna PR entra sin tests de lo que añade — la cobertura no baja del 80 %
- Toda migración es compatible con la versión anterior del código (expand-contract)
- Todo endpoint nuevo se añade a `packages/contracts` **antes** de implementarse
- Toda decisión arquitectónica no trivial genera un ADR en `docs/adr/`
- Toda alerta que pagina tiene su runbook antes de activarse
- Ningún secreto en el repositorio — gitleaks bloquea el push
- Las escrituras que el usuario percibe como instantáneas se hacen optimistas en el cliente
